# Candidate Knowledge Staging

Status: NON-CANONICAL

This area is for proposed transferable Knowledge Objects that have not completed canonical promotion.

Rules:

- Candidate knowledge is not canonical Expert Memory.
- Candidate status must not be used as established expertise.
- ARCHITECT may create candidates autonomously.
- Candidates should include evidence, applicability, limits, Recognition Cues, non-sensitive structural context, confidence, privacy/provenance review and expected behavioral impact.
- Epistemic learning validation may be performed by ARCHITECT.
- ARCHITECT Maintainer authorization is still required for canonical promotion.
- ARCHITECT Maintainer approval is governance authorization, not evidence.
- `validated` is achieved only after applicable epistemic criteria, ARCHITECT Maintainer authorization, and successful canonical EKB write. Before write, an authorized object remains `candidate` pending promotion.
- If no verified write path exists, the candidate remains proposed rather than canonically promoted.


## Permanent-repository privacy rule

Any candidate stored in the permanent ARCHITECT repository must already be de-identified.

Do not store raw:
- personal names;
- internal document names;
- financial figures;
- confidential source excerpts;
- sensitive Engagement evidence.

Keep raw evidence Engagement-side. Candidate `Evidence` uses a safe summary or opaque reference.
